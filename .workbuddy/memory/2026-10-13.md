**问题二：是否接入推荐/过滤逻辑 → 没有。**
- (A) `BoostDislike.refresh()` 只做「清理失效卡片 + 给新卡注入 ⋮」；对已上报卡片仅 `continue` 跳过注入，**从不隐藏/移除卡片**（ADR 0008 有意如此）。

## 排查：全屏醒目留言浮层「候补不补位」（未改动源码，待决策）

**现象**：显示窗（3 条）内某条 SC 到期消失后，超出上限的候补不会自动顶入，需刷新页面。

**代码定位（已确认，非猜测）**：
- 浮层**只有两个重新渲染的触发点**：① 取数层 `onUpdate`（每 10 秒轮询 / `close()` / `setRoom()` / `stop()`）；② 宿主重建后的回填 `if (remounted) render(...)`（`content.js:225 / 243`）。`render()` 之外没有任何重算路径。
- 浮层自持的**每秒到期清扫**（`superchat-ui.js` `_tick()`）只做「从 `_cards` 删除 + 播退场」，**完全不重算显示窗、不更新折叠计数** → 本地到期路径天然「只出不进」。
- 因此补位在现行架构下**只能靠取数事件**：本地到期 → 最多迟到一个轮询间隔（10s）；取数层若停摆 → 永不补位。
- 取数层 `_sweepExpired()`（`superchat.js`）与浮层 `_tick()` 是**两套独立的到期判定**（10s / 1s），各删各的，是"删了没人补"的结构性来源。
- `poll()` 用 `_inflight` 互斥且**无超时兜底**（`superchat.js:86-101`）：一次 `fetch` 挂住 → `_inflight` 永久为真 → 轮询彻底停摆 → 只有刷新页面（重注入 content script）才恢复。这是"必须刷新"的候选致命成因。
- 已确认 `close()`（点 ×）会经 `items.delete → _emit → render` **立即补位**，故「× 能立刻补位、到期不能」可作为区分根因的关键判据。

**术语缺口**：CONTEXT.md「折叠」只定义了 +N 汇总，**缺**「显示窗 / 候补 / 补位」三个词；已向用户提出规范的术语候选。

**待决策（已抛 grill 第 1 轮）**：复现形态与判据、显示窗与候补的归属（浮层自持 vs 取数层驱动）、补位与退场动画的时序、到期判据以谁为准、是否顺带给轮询加超时看门狗、术语与文档落档。

## 落地：SC 显示窗 / 候补 / 补位（同日完成，已提交 95ebf70）

**用户裁决（两轮 grill 全 ok）**：① 补位归属选 A——浮层自持「最后一次已知的可见列表」，本地删卡即就地重算显示窗，不等轮询；② 退场与补位同时跑；③ 到期判据以本地 `end_time` 为准；④ 加超时看门狗；⑤ 采纳术语并补 ADR；⑥ 不加 popup 开关，按纯 bugfix 处理。

**两条根因（已用本地冒烟对 HEAD 旧代码复现）**：
1. 浮层自持的每秒到期清扫（`superchat-ui.js` `_tick()`）**只删卡不重算显示窗**，而重渲染入口只有取数 `onUpdate` 与宿主重建回填 → 本地到期路径"只出不进"，候补最快也要等下一轮 10 秒轮询。
2. `superchat.js` `poll()` 用 `_inflight` 互斥**无超时兜底**，一次 `fetch` 挂起即永久停摆 → 只有刷新页面（重注入）才恢复，"必须刷新"的致命成因。

- `content/superchat.js`：删除第三套到期清扫 `_sweepExpired()`，判据收敛到 `visible()`；`poll()` 加 `AbortController` + `SuperChatFeed.TIMEOUT`（默认 8s，可经构造参数 `timeout` 覆盖以便测试）超时中止，`finally` 保证 `_inflight` 复位；`stop()` 顺手中止在途请求；迟到响应按 `!this._on || this.roomId !== room` 丢弃（顺带修掉"切房后旧房间响应污染新列表"的既有隐患）。

**踩到的环境坑（重要，下次直接用）**：
- **隐藏/被遮挡的标签页会被浏览器暂停 `requestAnimationFrame`**（实测首轮 `raf=0` → 浮层逐帧循环与 `_enter` 的高度赋值一并停摆，卡片塌成 0 高，断言整片失败）。这不是被测代码的问题。解法两条：① `tab_focus` 把标签页提到前台（`selected:true`）后重跑，即拿到真实帧（`raf=1053`）；② 页面内给 rAF 加 120ms 兜底（退化为定时器驱动）并分别记录 `rafCount` / `rafFallback`，使断言可跑且能区分"代码错"与"标签页没被渲染"。

- `tabs_new` 的 url 只接受 `http(s)://`，`file://` 不行，故必须起本地静态服务器（绑 `127.0.0.1`）。

- 渲染性能与合成稳定性（踩了很多坑，值得记住）：
  - **渲染耗时 87% 在截图编码**，不在画布绘制。基准：仅绘制 44ms/帧、PNG 截图 324ms/帧、PNG `optimizeForSpeed` 155ms/帧、JPEG 103ms/帧。所以 `optimizeForSpeed: true`（zlib 9→1，画质无损）是最大杠杆，全片 421s → 236s。
  - 背景静态部分（底色/辉光/竖透视线/地平线渐变）按强调色缓存成**离屏画布**，逐帧只 `drawImage`；粒子按亮度分 4 组批量填充（46 次 → 4 次）。这就是「不逐帧重画」的正确用法。
  - **不能**把透视网格整体烘焙成 PNG：横向那些线是逐帧滚动的，且 `y = HZ + p^1.9·…` 非等距，图片平铺位移模拟不了「向观众涌来」。
  - **ffmpeg 单次写长文件会被杀软/索引锁住**（约 8–9MB 时开始），表现为编码中途 CPU 归零卡死、`mv` 报 `Device or resource busy`。对策：**分段编码**（每段 10s / 300 帧）再拼接，每段文件小就不会被锁。
  - 拼接错位的两个坑：① 分段带 `-output_ts_offset` 时拼接器又按累计时长加一次，**偏移被算两次**；② `overlay` 的输出时间戳跟随**主输入**，主输入若走过 `-ss`，其时间戳不规整会传下去。
  - 终解：分段用 **`-fps_mode cfr -r 30`** 强制恒定帧率，不带 `-output_ts_offset`；清单里给每段写 `duration`。结果 1795/1795 帧、时间戳跳变 0 处。
  - 沙箱会拦截批量 `rm`（>50 文件进回收站）与 `rm -rf`；输出文件改用**每次唯一**的临时名（`.c$$`）绕开被占用的旧文件。
  - 成品：`B站音量增强-宣传片.mp4` 59.83s / 1920×1080 / 30fps / 15.2MB，全解码无错。
