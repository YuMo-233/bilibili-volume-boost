## 排查：「当前视频开关」（点踩）换页不重置 / 持久化疑问 / 撤销时效

**事实（读码 + 桩件验证，未改任何源码）**

- **开关是 UP 主级语义**：`_report(info, REASON_UP)` → 写 `blockVideo(bvid,4)` + `blockUp(mid)`；`_syncToggle()` 用 `DislikeStore.isUpBlocked(mid)` 回显。故"同一 UP 的另一条视频仍是 ON"**是设计使然**。误解来源是术语：「当前视频开关」让人以为是"对当前视频不感兴趣"，实际是"屏蔽该 UP 主"。
- **持久化是有的**（上一轮刚加的 `ups`/`videos` 桶）：重进同一 UP 的视频仍回显 ON。若观感上没有，先确认扩展已重新加载。
- **真实缺陷（桩件已复现）**：SPA 换页瞬间地址栏已变、DOM 里 `.up-info-container` 的 UP 链接仍是旧值 → `_currentVideo()` 配出「新 bvid + 旧 mid」→ 开关错误显示 ON，DOM 追上后自行纠正。**同一窗口内点击会把上报打到错误的 UP 主上**（`_toggleReport` 用 `_currentVideo()` 重新解析）。
- **撤销被绑死在远端成功上**：`_cancel()` 先 `await _post(CANCEL_URL)`，成功才 `unblockVideo/unblockUp`。一旦远端拒绝（记录过旧 / reason_id 不匹配），开关与卡片浮层都永远撤不掉，只剩 popup「清空屏蔽记录」。
- **取消时效调研**：无任何公开文档给出数值阈值。B 站把「不感兴趣」记为可长期管理的记录（历史记录页有「已拉黑/不感兴趣」筛选可长期取消；卡片上的「撤销」刷新后即消失）。故不存在确证的硬性过期，但结论是**不能把本地解除绑死在远端成功上**。

**待决策（已抛出 grill 轮次）**：① 开关语义（UP 主级正名 / 改为视频级 / 两级并存）；② 撤销是否必须等远端成功；③ 换页瞬间旧 mid 的修法。

**产物**：临时验证脚本 `%TEMP%/bv-dislike-smoke/toggle-reset.js`（未入仓），6 个用例 5 通过 1 失败——失败那条正是旧 mid 残留。
