# 0006-注入就绪判定与悬停残留清理

**状态**: accepted

**决策**: 增益条在**控件就绪**前保持隐藏且不可交互;就绪判定为「锚点存在 + 锚点可见 + 锚点位置连续两次采样一致」;锚点 5 秒内始终未出现则**兜底放行**(回退到追加到控制栏末尾);宿主每次被移动后**清除悬停残留**。

**要修的问题（实测）**: 页面加载期增益条会短暂出现在播放器**右下角**,与全屏按钮同位,用户去点全屏时被它挡住;控件加载完成后它被移到音量按钮旁,但面板会**一直展开不自动收起**。

**根因（读码确认）**:
1. `BoostUI.mount()` 在 `findAnchor()` 失败时**兜底 `slot.appendChild(host)`**（ui.js 原 119-121 行）——锚点尚未渲染,宿主就落到了控制栏末尾,即右下角。
2. `content.js` 的 `ensureUI()` 每次 DOM 变化与每 2 秒都调 `relocate()`,锚点出现后把宿主移到音量按钮右侧。
3. 悬停残留:`.bv-open` 在 `mouseenter` 时加上、**只在 `mouseleave` 时移除**。**元素在鼠标静止时被移动,浏览器不会补发 `mouseleave`**,于是 `.bv-open` 永久残留,面板一直展开。

即故障由「加载期挂到了错误位置」与「位置变更时悬停状态未清理」两件事叠加而成,只修其一都会在别的时机复现。

**理由**:
- 隐藏宿主直接消掉加载期这个时间窗:错误位置与误触都不再可见、不可交互。
- 就绪判定用**客观信号**（锚点可见且位置不再变）而非固定延时:固定延时在慢机器上不够、在快机器上白等;只看「锚点存在」也不够——锚点可能已渲染而整个控制栏还在做淡入/位移,此时插入仍会被移动一次。
- 隐藏方式选 `visibility` 而非 `display`:宿主是插在原生音量按钮**旁边**的,`display:none` 会让占位消失,显示瞬间把右侧原生按钮整体推开一次,这个位移本身又可能触发一次「鼠标没动、元素动了」,把原问题换个时机再现。
- 清理悬停残留是治本:控制栏在进出全屏、切换清晰度、直播切流时都会重排,每次 `relocate()` 都可能让面板卡在打开状态。

**判定细则**:
- 锚点可见 = `getBoundingClientRect()` 宽高均 > 0。锚点为 `display:none` 时 rect 恒为 0,若只看位置是否变化会被误判为「稳定」。
- 连续两次采样:首次取样记录签名,第二次签名一致即放行。为避免依赖 2 秒轮询(最坏拖到 4 秒),首次取样后**主动补一次 300ms 后的复核**。
- 就绪是**一次性闩锁**:放行后不再因控制栏后续重排而重新隐藏,否则进出全屏会闪。
- 兜底时限 5 秒:足够区分「加载慢」与「该播放器变体确实没有锚点」,保留原有兜底能力,不造成功能失效。
- 清理悬停残留消除的是 `.bv-open` 这条**类驱动**的锁;若指针恰好停在移动后的新位置上,CSS `:hover` 仍会成立,但该状态在指针下一次移动时自然解除,不会长期残留。就绪前的 `pointer-events:none` 则从根上杜绝了加载期的悬停。

**取舍**:
- 增益按钮最坏延后约 300ms–5s 出现;兜底路径下仍会落在控制栏末尾(可见但位置非最右手边)。
- 隐藏作用于 Shadow DOM 内的 `.bv-box` 而非整个宿主:`.bv-toast` 是 shadow root 内的兄弟节点,快捷键反馈的 toast 在就绪前依然可见。
- 隐藏期间宿主设 `pointer-events:none`,保证其占位区域也不可能拦截点击。

**后果**:
- 加载期不再出现「右下角的增益按钮」,也不会出现「面板卡在展开态挡住全屏按钮」。
- 就绪前的快捷键与音量记忆读写不受影响,只是角标 toast 之外的滑块 UI 不可见。
