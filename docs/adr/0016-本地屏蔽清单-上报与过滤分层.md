# 本地屏蔽清单:上报与过滤分层,让标记过的内容不再重复出现

搜索页与详情页相关推荐的「不感兴趣」此前只做了两件事：调官方接口上报、把当前卡片切到**已反馈态**。结果是刷新页面后被标记的内容照常回来——**上报是服务端信号，不等于本地不再打扰**。决定：新增一层本地持久化的**屏蔽清单**，把「上报」与「过滤」拆成两层，并由清单驱动卡片的呈现。

## Status

accepted

## 背景（排查结论）

**问题一：是否真的调用了官方通道——是。** `content/dislike.js` 的 `_post()` 打 `POST x/web-interface/feedback/dislike`，撤销打 `.../dislike/cancel`，`reason_id` 1=内容不感兴趣、4=不想看此UP主；UI 层只有 `onReport()` 返回成功才 `markReported()`（`dislike-ui.js`），失败仅 toast，卡片保持原样。故**不存在"只隐藏不上报"的动作路径**，"前端隐藏"永远发生在上报成功之后。与独立参考实现（同类用户脚本的 web 源）逐字段比对，接口路径 / 方法 / `app_id=100&platform=5&goto=av&id={aid}&feedback_page=1&reason_id&csrf` 全部一致。

但 `code===0` 只代表**服务端接收成功**：该接口喂的是 B 站的**个性化推荐流**，对搜索页结果（按查询相关性排序）与详情页相关推荐（内容相似度召回，`archive/related`，免登录无 WBI）都不生效，且服务端生效有延迟。

**问题二：是否接入了推荐与过滤逻辑——没有。** 三条叠加：
1. `BoostDislike.refresh()` 只做「清理失效卡片 + 给新卡注入 ⋮」，对已上报卡片仅 `continue` 跳过注入，**从不隐藏或移除卡片**；
2. 已上报集合是**内存 Set**，刷新即清零，于是每张卡又被当成新卡重新注入；
3. 服务端降权本来就不作用于这两个数据源（见上）。

## 决策要点

- **分两层，职责单一**。**信号层**＝官方上报（保留，唯一能真正影响推荐系统的通道）；**过滤层**＝本地屏蔽清单（新增，唯一决定"现在还打扰不打扰我"）。不要让上报逻辑兼职做过滤。
- **清单独立存储**：`chrome.storage.local` 的独立键 `bv.blocklist.v1`，不并入音量记忆的 `volumeBank.v1`——语义不同，且不会被音量记忆的 v1→v2 迁移与 `.video/.live` 分桶逻辑波及。结构：
  `{ version, hide, videos: { bvid: {t, r} }, ups: { mid: {t, n} } }`。
- **写操作串行**：沿用 `memory.js` 已验证的 `_enqueue` 串行队列模式，消除多个"读-改-写"副本互相覆盖的竞态；另维护一份内存镜像供 `refresh()` **逐卡同步判定**，避免每张卡片一次异步读盘。
- **配额与淘汰**：视频级 2048、UP 主级 512，各自独立按写入时间 LRU 淘汰（与音量记忆同一思路）；无过期。
- **落库时机不可颠倒**：上报**成功**才写清单，撤销**成功**才移除。避免"上报失败却留下本地屏蔽"，也避免"撤销失败却放行"。
- **命中后的呈现**：默认沿用 docs/adr/0008 的取舍——卡片**原位**呈已屏蔽态（磨砂 + 只盖封面的浮层 + 隐藏信息区，保留撤销入口），列表**不跳动**；另外在 popup 提供一个 **「彻底隐藏」** 开关，打开后已屏蔽卡片整块撤下（宿主卡片 `display: none`，解除时按原值还原）。隐藏是用户明确选择的行为，此时列表重排正是预期结果。
- **判定与呈现分离，且以 UI 状态为幂等基准**：`DislikeStore.match(info)` 只回答"该不该屏蔽"（视频级优先于 UP 主级），`_applyBlocked()` 只负责把呈现对齐到判定结果，并拿 UI 自身的 `reportedReason()` 做比较——用户点菜单上报 / 点撤销都会即时改变 UI 状态，故这里只需补"清单与 UI 不一致"的那部分差，不会重复施加。**副产品**：popup 清空清单、切换隐藏模式都不需要任何额外通知路径，下一轮复核自动收敛。
- **清单变化即复核**：`content.js` 监听该键的 `storage.onChanged` → `invalidate()`（内存镜像失效）→ **重新 `ensure()` 读盘** → `syncDislike()`。必须先重读：`refresh()` 有"清单未就绪不注入"的闸门（否则命中清单的卡片会先以新卡形态闪一下 ⋮），不重读的话改动会被闸门直接吞掉。
- **mid 零请求可得（修正 ADR 0008 的过时结论）**：实测（2026-10）搜索页 `.bili-video-card` 的 `.bili-video-card__info--owner` 就带 `//space.bilibili.com/{mid}`（50 张卡中 42 张有该链接，其余是骨架屏），与详情页推荐卡一致。故「不想看此UP主」在搜索页**无需任何补取请求**即可生效，UP 主级过滤在搜索页与侧栏全面可用；`_fillUp()` 降级为"卡片结构变化时的兜底"。
- **补 `track_id`**：部分卡片（`.bili-video-card__wrap` 变体）把 `track_id` 挂在视频链接的 query 里，它是"反馈归因到哪个推荐位"的字段，有则随上报带上、无则不填（推荐卡实测不带）。
- **`mid` 未知时整个字段不发**，不退化成 `mid=0`：与其向服务端声明一个并不存在的 UP 主，不如让内容级理由保持纯内容级语义。（参考实现用 `mid=0` 兜底，此处有意不跟。）
- **当前视频开关与清单同源**：进页面时若该 UP 主已在清单里，开关直接呈激活态；撤销该 UP 主级屏蔽会移除整条 mid 记录，该 UP 主的其它卡片随之恢复（它们此前是靠 mid 命中清单的）。
- **不改动宿主 DOM 结构**：隐藏与磨砂一律只写**内联样式**，与 docs/adr/0008「绝不往 B 站 Vue 管理的节点里插子节点」一致；Vue 重渲染会抹掉内联样式，下一轮 `refresh()` 复核自动重施。

## Considered Options

- **只保留官方上报，接受"刷新后复活"**：用户明确不接受该现象，且服务端信号对搜索页/侧栏本就不生效，否决。
- **沿用会话去重集合 + 叠加清单（双轨）**：两套真值会漂移（一个是内存一个是盘），同卡在两处的判定可能不一致，否决，改为清单单一真值。
- **默认硬移除卡片**：与 docs/adr/0008 冲突（会造成列表跳动，也不符合原生"原位覆盖"），否决；改为默认已屏蔽态 + 可选隐藏。
- **为搜索页逐卡调 `view` 接口补 mid**：一次搜索页可有 30+ 张卡，N 次请求有被限流风险；且实测 mid 本就在 DOM 里，纯属多余，否决。
- **`mid` 兜底 `0`**：见上，否决。
- **在卡片上插入自己的隐藏占位节点**：会破坏 SSR + hydration（ADR 0008 已踩过），否决。
- **用 `visibility: hidden` 保留槽位来"隐藏"**：会在列表里留空洞，观感比跳动更差；默认不需要隐藏，故不考虑。

## Consequences

- 新增一个 `chrome.storage.local` 键与两类配额上限（2048 / 512），总占用有界。
- 搜索页与详情页相关推荐对"已在清单内的内容"实现**零网络请求**的本地过滤；**B 站服务端的降权仍只作用于个性化推荐流，插件无法改变这一边界**——这一点必须对用户保持诚实。
- 撤销入口只剩卡片浮层里的「撤销」与 popup 的「清空屏蔽记录」；不存在"仅解除本地屏蔽但保留服务端上报"的中间态。
- 「已屏蔽态」与「已反馈态」共用同一套视觉与同一份 UI 代码（`markReported`），没有第二套样式需要维护；代价是二者在视觉上不可区分（这是有意的：对用户而言语义相同）。
- 依赖 `bv2av` 本地换算与卡片 DOM 结构；B 站改版后若 `__info--owner` 链接消失，UP 主级过滤会在搜索页退化为"仅对已知 mid 生效"，届时需重新采集选择器。
