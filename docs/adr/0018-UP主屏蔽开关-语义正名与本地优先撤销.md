# UP 主屏蔽开关:语义正名、撤销本地优先、识别就绪前不可点

播放器页操作栏那个「点踩」控件此前有三个问题：换页后状态看着不重置、看起来没有持久化、以及一旦远端拒绝撤销就永远关不掉。逐条查清后决定：**保持它的 UP 主级语义但正名**，把**撤销的裁判权从服务端收回到本地**，并让"谁是当前 UP 主"只认一个来源。

## Status

accepted

（本 ADR 取代 ADR 0008 中「当前视频开关」的称谓；其"该控件只承载「不想看此UP主」这一条真实信号"的结论不变。）

## 背景（排查结论）

- **"换页不重置"一半是设计、一半是真缺陷。**
  - 设计那半：该控件走 `reason_id=4`，同时写 `blockVideo(bvid,4)` 与 `blockUp(mid)`，回显只看 `isUpBlocked(mid)`——所以同一位 UP 主的**每条**视频都呈同一状态。这是**正确表现**，问题出在术语「当前视频开关」让人以为是"对当前视频"。
  - 缺陷那半：SPA 换页瞬间 `location.pathname` 已变、而 DOM 里 `.up-info-container` 的 UP 链接仍是上一条视频的。`_currentVideo()` 的 bvid 取自 URL、mid 取自 DOM，于是拼出「新视频 + 旧作者」这种现实中不存在的身份 → 开关亮出**错误的激活态**；同一窗口内点击，还会把上报打到**错误的 UP 主**上。桩件复现：6 个用例 5 过 1 挂，挂的正是这条。
- **持久化其实已在**（`bv.blocklist.v1` 的 `ups` 桶，见 ADR 0016），跨刷新存活；观感上的"没有持久化"来自上一轮未重载扩展。
- **撤销被绑死在远端成功上**：原 `_cancel()` 先 `await _post(CANCEL_URL)`，成功才解除本地屏蔽。任何远端拒绝（记录过旧、`reason_id`/mid 对不上、接口变更）都会让用户**永远关不掉开关**，只剩 popup 清空。
- **取消时效调研**：没有任何公开文档给出数值阈值。B 站把「不感兴趣」记为可长期管理的记录（历史记录页有「已拉黑/不感兴趣」筛选，可长期取消；而卡片上的「撤销」刷新后即消失）。故正确结论不是"猜一个过期时间"，而是"**别让本地状态依赖它**"。

## 决策要点

- **保持 UP 主级语义并正名**（用户裁定）：术语「当前视频开关」→「**UP 主屏蔽开关**」，悬停提示改为「屏蔽该 UP 主（再点一次撤销）」，文档写明"同一位 UP 主的每条视频呈同一状态、换页不重置是该语义的正确表现"。不做成视频级——网页端没有可用的点踩接口，该控件只能承载这一条真实信号；而"对单条内容不感兴趣"已由卡片 ⋮ 的「内容不感兴趣」覆盖。
- **撤销本地优先**：远端 `/dislike/cancel` 降级为**最佳努力**，连"请求本身抛错"都要兜住；无论远端如何，本地屏蔽一律解除。返回 `{ ok, remote }`（`ok`=本地是否真的解除，`remote`=服务端是否接受），UI 在 `remote=false` 时如实提示「已解除本地屏蔽，B站端撤销未成功」。
  上报侧**刻意相反**：没拿到服务端确认就不落清单。不对称是有意的——上报失败留个本地屏蔽是"多屏蔽了"，撤销失败关不掉则是"用户失去对自己界面的控制权"。
- **"谁是当前 UP 主"收敛为唯一来源**：由 `content.js` 把它**已识别就绪**的结果注入控制器（`new BoostDislike(() => current)`），`_currentVideo()` 不再从 DOM 现取 mid。
- **识别就绪前开关置灰且不可点**：既不像原实现那样亮错状态，也不像"整个撤下"那样让每次自动连播都眨一下眼。置灰期间把激活态归零，并拦截点击（防误报）。这是 Q3 的裁定 (b)。
- **识别就绪即回显**：`setCurrent()` 在识别结果变化时立刻驱动一次 `syncDislike()`；否则要等下一轮 refresh（DOM 变更或 2 秒 tick）才解除置灰。
- **`_post` 承诺"只返回布尔、绝不抛出"**（参数组装与 `fetch` 同处 try 内），调用方才敢只做一次 await——否则"本地一定解除"这条保证会被一次异常击穿。
- **卡片路径不受影响**：搜索页/相关推荐卡片的身份仍从卡片自身 DOM 提取（那里没有"滞后"问题）；`_fillUp()` 继续做 mid 兜底。

## Considered Options

- **改为视频级（`reason_id=1`）**：用户裁定否决——会丢掉"在播放器页直接屏蔽这个 UP 主"的能力，也会让"点踩"的语义继续含糊。
- **未就绪时整个撤下开关**：实现最省，但每次自动连播都会眨眼；否决。
- **只堵上报、显示照旧**：留着"亮错"现象，正是用户报的问题本身；否决。
- **记录一个"撤销过期时间"**：无公开阈值，属臆测；否决。
- **维持"远端成功才解除本地"**：会让用户永久锁死；否决。

## Consequences

- 开关的显示与上报只依赖「识别结果 + 屏蔽清单」，DOM 滞后不再影响正确性。代价是换页后有 0.25~1.2 秒的置灰期（识别耗时），可接受。
- 本地与远端可能出现不一致（本地已解除、B 站端仍记着 dislike），用 toast 如实告知，不再假装成功；popup 的「清空屏蔽记录」仍是兜底出口。
- 卡片 ⋮ 的撤销走同一条 `_cancel`，故"本地优先"对它同样生效。
- 控制器与 `content.js` 之间多了一条"识别结果"依赖：`_currentVideo()` 的 mid 来源单一，但也意味着**识别彻底失败时开关永不解除置灰**（此时 domSniff 与 sniff 事件都失败了，属于既有识别链路的兜底范畴）。
